## 1. 第一章 引言：为什么需要可更新 PSI

### 1.1 研究背景：一次求交解决不了持续变化的数据

设医院 A、B 各有一批患者标识，希望找出共同患者，但不能直接交换各自完整名单。一次 PSI 可以完成这次匹配。如果第二天 A 新增 20 人、B 删除 10 人，前一天的交集就可能过时。最直接的办法是把两边当前的完整名单重新输入 PSI；功能上没有错，但相同数据反复参与密码计算和传输。

UPSI 希望把“一次性的私有匹配”变成“有状态的私有维护”：保存上一次允许得到的交集与必要的本地数据库，之后根据变化更新结果。这里的状态不是公开的共享数据库，各方仍分别维护自己的私有输入。

新增和删除的难度不同。新增需要找出新的匹配；删除还要判断旧交集中哪些匹配已经失效。一方删除自己的非交集元素，不应让另一方因此知道这个私有元素曾经存在。

### 1.2 现有方案的限制：弱删除、任意删除与历史关联

“删除”需要看具体定义。有些方案把元素标为不再参与当前结果，但在协议状态或隐私保证上仍受原集合限制；另一些方案只支持新增，无法直接承接任意增删。不能把“用户界面上删除了一条记录”理解成密码协议一定实现了同样强的删除功能。

本文希望支持正常集合语义下的任意新增和删除，还允许某元素在不同轮次经历“加入—删除—再次加入”。这带来跨轮问题：如果协议暴露某个稳定中间值，对方可能在第三轮认出这是第一轮出现过的私有元素。即便不知道其真实内容，额外知道“它重复出现过”也可能超出允许泄露。

### 1.3 论文的切入点与贡献

每轮新增集合相对完整集合通常很小，因此可让“小更新集合”查询“大数据库”，使用非对称 PSI。双方都可能新增，所以要做两个方向。各方向先获得局部新增交集，再通过 PSU 合并。删除则利用旧交集，在本地筛出受影响部分，再安全求并。

论文的贡献是这套 UPSI 组合设计、面向持续更新的多轮 OPRF、对允许泄露的讨论，以及实现和性能评估。RR22、APSI 与 PSU 不是本文从零发明的；应分别理解借用的组件和作者给出的上层构造。

引言中的性能提升也要连着比较对象读：相对于另一种支持增删的 UPSI，可能有几个数量级的提升；相对于高效静态 PSI，则要看完整规模、更新量和网络条件。不能把某个最优倍数当成所有情况下的保证。

## 2. 第二章 相关工作：PSI、APSI、PSU 与 UPSI 的关系

### 2.1 PSI 的技术路线：相同功能不代表相同实现

DH 型方案利用群指数与哈希得到可匹配表示，直观但通常包含较多公钥运算。OT 型方案把匹配转换为大量小型不经意选择；通过 OT 扩展，用少量昂贵的基础 OT 生成大量较便宜的 OT，减少平均成本。VOLE 与 OKVS 型方案则利用相关随机向量和线性编码关系，构造匹配标签。

这几条路线都旨在保护交集外输入。它们不是“旧协议会公开集合、新协议才不公开”的区别，而是在不同安全模型、规模和网络下有不同效率。本文初始化使用 RR22，对应 VOLE 与 OKVS 这条路线。

### 2.2 APSI 为什么适合小集合查询大集合

假设 Alice 有一百万项，Bob 只有一百项。对称协议未必充分利用这一差距；非对称 PSI 通过预处理大数据库、分桶、同态求值等方式，把在线查询组织得更高效。

APSI 的“不对称”首先指输入规模与计算分工，不等于只保护一方隐私，也不等于双方必须公开规模不同这一事实之外的元素信息。至于谁获得结果，要看具体协议接口；本文后面一方向查询由小集合方得到匹配。

### 2.3 PSU 与 RPMT：从求交转向补齐并集

PSI 想知道共同部分；PSU 想得到合在一起的元素。例如 Alice 有 \(\{2,6\}\)，Bob 有 \(\{6,8\}\)，交集是 \(\{6\}\)，并集是 \(\{2,6,8\}\)。Bob 要得到并集，只需补上自己没有的 2，但不能因此获知 Alice 对每个已有元素的持有情况。

RPMT 是反向私有成员测试。在本文介绍的 PSU 功能中，持有候选元素的一方参与测试，持有集合的一方得到相应成员位，元素方不获知测试结果。配合 OT，集合方在缺少候选项时取得它，已经持有时取得占位符。真正实现还需分桶、填充和隐藏位置，后面会完整展开。

### 2.4 UPSI 的研究问题不止“怎样更快”

静态 PSI 一次执行安全，不意味着把某个中间状态长期保存、反复更新就自动安全。持续协议还要回答：重复输入是否可关联，删除是否真正生效，哪些规模可以泄露，单方还是双方获得交集，初始化成本多久能摊销。

本章先认识四类功能及其关系；第四章才把具体公式和通信接起来。**这里不用先记下所有缩写的实现细节，但要记住功能不同：OPRF 生成函数值、PSI 求交、PSU 求并，UPSI 维护交集。**

## 3. 第三章 预备知识：符号、更新语义与安全定义

### 3.1 阅读后续公式需要的数学工具

安全参数 \(\kappa\) 控制攻击成本的目标量级，论文实验采用 128 位计算安全参数。它不是“集合里必须有 128 个元素”，也不是任意选择 128 位模数就能安全。

群 \(G\) 是执行指数运算的代数空间。群元素的运算与指数的模运算分属两个空间，例如教学例子用模 23 的群元素、模 11 的指数。盲化逆元应在指数空间求，混淆这两个模数会导致去盲化失败。

有限域 \(\mathbb F\) 支持加减乘与非零元素求逆，常用于 VOLE、OKVS 线性关系和多项式计算。\(\mathbb F_{101}\) 中 \(-20=81\)，不能把域运算结果按普通有理数算完就忽略取模。

密码学哈希把输入映射到协议要求的空间。随机预言机是证明时使用的理想化模型：一致地回答相同查询，并使未查询点看起来随机；它不意味着程序每次对相同输入都返回不同值。实际使用哈希函数时仍须满足协议的编码与域分离要求。

### 3.2 理想功能：用来规定能知道什么

理想 PSI 可以想成可信计算者：接收双方集合，只向指定结果方返回交集。理想 PSU 返回规定的并集。UPSI 理想功能保存轮次状态，依次接收合法更新，输出规定的新交集和允许的泄露。

这里的“可信计算者”是安全定义的参照，不要求实际部署第三方。真实协议的目标是：没有这个可信者，也不让参与方学到超过理想功能的信息。

例如双方允许知道每轮交集，那么“交集中的 6 本轮消失”本身不应再被称作额外泄露；但某个始终没进入交集的私有元素跨轮重复出现，若被协议暴露，就可能是额外信息。判断隐私时必须先固定允许输出，再讨论超出的部分。

### 3.3 半诚实模型：按步骤做，仍可能分析全部记录

半诚实方会按规定生成消息、执行计算，却可能保存所有输入、随机数、报文和输出并联合分析。因而“它没有故意发送假消息”并不等于可信。

本文安全结论针对这个模型。若一方伪造集合、使用非法群元素或恶意构造查询，需要更强的输入检查与恶意安全论证，不能直接引用半诚实证明解决。

### 3.4 上一轮、本轮和新增删除

用 \(X_i,Y_i\) 表示第 \(i\) 轮更新后的集合，\(I_i=X_i\cap Y_i\) 表示本轮交集。新增集合用上标 \(+\)，删除集合用上标 \(-\)：

$$X_i=(X_{i-1}\setminus X_i^-)\cup X_i^+,\qquad Y_i=(Y_{i-1}\setminus Y_i^-)\cup Y_i^+.$$

例如 Alice 原来有 \(\{1,2,3\}\)，删除 2、添加 4，更新后就是 \(\{1,3,4\}\)。集合没有重复元素，“添加已有元素”也不会让数量增加。

论文 IV-C 采用以下正常化规则：

| 规则 | Alice 一侧的写法 | 含义 |
| --- | --- | --- |
| 新增元素不在上一轮集合里 | \(X_i^+\cap X_{i-1}=\varnothing\) | 不把已经存在的元素再次算作新增 |
| 删除来自上一轮集合 | \(X_i^-\subseteq X_{i-1}\) | 不删除不存在的元素 |
| 同轮增删互斥 | \(X_i^-\cap X_i^+=\varnothing\) | 同一轮不对同一元素先删又加 |

Bob 一侧同理。这些是协议分析使用的输入规则，不是随机选择的条件；第三条在前两条下也可推得。**它们不禁止跨轮“添加、删除、重新添加”**，跨轮关联正是后面要研究的问题。

### 3.5 N 和 Nᵘ：不是双方必须一样大

论文复杂度分析和实验简化为：

$$|X|=|Y|=N,\qquad |X_i^+|=|Y_i^+|=|X_i^-|=|Y_i^-|=N^u.$$

这里的 \(N^u\) 是“更新规模”的符号，字母 \(u\) 表示 update，不是要求把 \(N\) 再进行一次数值乘方。例如 \(N=2^{20},N^u=2^8\) 表示每方初始约一百万个元素，每类更新各 256 个。

相等是分析和测试设定，图 8 的集合运算本身不要求双方集合规模或增删数量相等。规模不等时，应分别设置两方向的查询、建库和通信参数，不能照搬等规模实验的秒数。

**规模是否保密要看安全定义和接口。**本文允许泄露每方的更新规模；批次数、报文长度和所选参数也可能透露规模或上界。不能默认“元素加密了，所以集合大小也保密”。若要隐藏实际规模，需要填充等额外机制。

## 4. 第四章 IV-A 基础组件：从底层技术到输入输出

### 4.1 基础 PSI 的角色：先求一次初始完整交集

论文图 4 的基础求交用 VOLE、线性 OKVS 和哈希构造标签；图 8 在初始化阶段调用基础 PSI，之后不在每个更新轮次重跑它。下面先按图 4 的变量解释，每个 Decode 都统一写成“编码结构在前、键在后”。

VOLE 提供相关随机性：

$$C=\Delta A+B.$$

此处 Alice 持有 \(A,C\)，Bob 持有 \(\Delta,B\)。向量和标量不是双方一起公开挑出的玩具数，而是通过 VOLE 协议获得的私有相关随机量。关系式成立不代表任意一方知道全部变量。

Alice 对自己的集合 \(X\) 建立线性 OKVS：

$$P\leftarrow\operatorname{Encode}(\{(x,H_2(x)):x\in X\}).$$

它保证输入键满足 \(\operatorname{Decode}(P,x)=H_2(x)\)。不在编码键集合中的输入不具有这条保证，也不能默认 Decode 返回报错、零或每次新随机数。固定结构、固定查询键的解码是确定的。

所谓“线性”，指对结构向量的线性：

$$\operatorname{Decode}(B+\Delta P,z)=\operatorname{Decode}(B,z)+\Delta\operatorname{Decode}(P,z).$$

这不是声称查询键本身可以相加，也不是所有键值存储都支持它。OKVS 的隐藏性质还有其随机值分布等适用条件，不是 Encode 这个名称自带任意输入隐私。

随后执行：

| 步骤 | Alice | Bob |
| --- | --- | --- |
| 生成编码消息 | 计算 \(A'=A+P\)，发给 Bob | 接收 \(A'\) |
| 得到关联结构 | — | 计算 \(B'=B+\Delta A'=C+\Delta P\) |
| 生成匹配标签 | 对自己的 x 计算 \(H_1(\operatorname{Decode}(C,x))\) | 对自己的 y 计算 \(H_1(\operatorname{Decode}(B',y)-\Delta H_2(y))\) |
| 匹配输出 | 接收 Bob 的标签，找出自身匹配元素 | 发送规定的标签集合 |

若 \(y=x\in X\)，则：

$$\begin{aligned}\operatorname{Decode}(B',y)-\Delta H_2(y)&=\operatorname{Decode}(C+\Delta P,y)-\Delta H_2(y)\\&=\operatorname{Decode}(C,y)+\Delta\operatorname{Decode}(P,y)-\Delta H_2(y)\\&=\operatorname{Decode}(C,y).\end{aligned}$$

第二行用线性，第三行用已编码键的正确性。标签相等时，Alice 结合自己的输入知道对应的交集元素。图 8 初始化需要双方得到交集，因此要匹配双输出的功能，不能停在单方输出就认为初始化结束。

### 4.2 基础 PSI 的数字例子：把 Decode 真正算出来

为避免直接假定一串解码结果，这里用一个**仅演示线性关系的三维模型**。它不是安全 OKVS，也不是实际 RR22 参数。域为 \(\mathbb F_{101}\)，Alice 输入 \(X=\{2,5\}\)，Bob 输入 \(Y=\{2,7\}\)，人为约定 \(H_2(2)=10,H_2(5)=20,H_2(7)=30\)。

定义三个演示用解码行：

$$\operatorname{Decode}(u,2)=u_0+u_1,\quad\operatorname{Decode}(u,5)=u_1+u_2,\quad\operatorname{Decode}(u,7)=u_0+u_2.$$

要编码 2→10、5→20，须满足 \(p_0+p_1=10,p_1+p_2=20\)。假设自由坐标**随机采样结果**是 \(p_1=3\)，得到 \(P=(7,3,17)\)。实际代入可得 Decode(P,2)=10、Decode(P,5)=20、Decode(P,7)=24；最后一项不必等于约定的 \(H_2(7)=30\)，因为 7 没被编码。

再假设相关随机量的一次示例取值为 \(A=(4,7,9),B=(6,2,8),\Delta=3\)，于是：

$$C=(18,23,35),\qquad A'=A+P=(11,10,26),\qquad B'=B+3A'=(39,32,86).$$

Alice 对 2、5 的哈希前值分别为 \(18+23=41\)、\(23+35=58\)。Bob 的计算为：

| Bob 的输入 | Decode(B′,y) | 减去 ΔH₂(y)，模 101 | 与 Alice 的值匹配吗 |
| --- | ---: | ---: | --- |
| 2 | 71 | \(71-30=41\) | 匹配 2 |
| 7 | \(39+86\equiv24\) | \(24-90\equiv35\) | 不匹配 |

哈希后识别出交集 \(\{2\}\)。这个例子说明“已编码键的项抵消”，不证明小域具有安全性；真实方案还须控制碰撞和失败概率。

**本块用到：**相关随机性、有限域、线性 OKVS、哈希。**本块没有使用：**APSI 的同态多项式查询、图 7 的多轮群盲化、PSU。不能因为两者都涉及随机化就把 VOLE 当成 MROPRF。

### 4.3 非对称 PSI：查询阶段如何进行

### 4.4 明文系数和加密查询是这一方向的分工

本文调用文献 [33] 的 APSI 查询阶段。以 Alice 为大集合持有者、Bob 为少量查询元素持有者：

1. Alice 在自己的数据库上组织匹配多项式，保存其系数。
2. Bob 把查询值或协议需要的查询幂进行同态加密，向 Alice 发送查询。
3. Alice 在密文上执行多项式求值，按协议处理响应，再返回加密结果。
4. Bob 持有对应私钥，解密并识别匹配项。

**Alice 不把数据库的明文多项式交给 Bob；Bob 也不需要先知道 Alice 的所有系数。**反方向查询时，Alice 与 Bob 的角色交换。

“Alice 加密系数，Bob 对自己的明文输入求值”是另一类可以讨论的 PSI 构造，不能拿它替换本文这里的通信方向。判断方向时始终问三个问题：谁有数据库、谁持有查询、谁掌握解密私钥。

### 4.5 用一个小桶算清楚为什么等于零就是匹配

设某个桶中的 Alice 标签是 \(\{2,5,9\}\)，Bob 要查标签 5 或 7。这里的 2、5、9 是**示意性的域元素标签**，不是声称真实 OPRF 会产生这些指定数。

在 \(\mathbb F_{101}\) 上，匹配多项式为：

$$P(t)=(t-2)(t-5)(t-9)=t^3-16t^2+73t-90.$$

查询 5 时 \(P(5)=0\)；查询 7 时：

$$P(7)=(7-2)(7-5)(7-9)=-20\equiv81\pmod{101}.$$

Bob 发出 \(\operatorname{Enc}(5)\) 后，Alice 同态计算的是 \(\operatorname{Enc}(P(5))\)，她自己看不到解密后的零；Bob 解密后才能识别匹配。这解释了“Alice 不知道 Bob 查了谁，却能替他计算”。

以上展示的是**匹配代数**，不是一份可以直接部署的完整安全协议。非匹配响应若未经适当处理，可能泄露数据库的代数信息。完整 APSI 的编码、参数、响应处理和安全机制不能省略。

### 4.6 为什么还需要哈希分桶、打包和预计算

如果把百万个标签全部写成一个多项式，次数太高，同态计算深度、密文噪声和通信成本都难以承受。论文所用方法通过大集合的简单哈希、小集合的布谷鸟哈希，让匹配候选进入相应桶，再对较小的桶计算。

实现还用到 SIMD 打包、分割和查询幂优化：一次密文运算处理多个槽位，减少重复工作。**分桶帮助安排计算，不能单独提供输入隐私；同态加密保护查询，但不能代替整个 PSI 安全证明。**

OPRF 后为什么还要 APSI？因为 OPRF 解决“怎样得到同一密钥下可匹配的表示”，APSI 解决“怎样在不直接公开这些集合的情况下进行成员匹配”。两者负责相邻的不同环节。

### 4.7 PSU 的底层流程：分桶、RPMT 和 OT 如何接起来

以 Alice 输入 \(A=\{2,6\}\)、Bob 输入 \(B=\{6,8\}\) 为例，只解释本文介绍的 PSU 思路，不让教学展开变成额外真实泄露。协议先按哈希规则分桶，并对桶填充、排列；填充位置使用占位符，桶的位置和长度不能随意暴露真实元素情况。

对 Alice 的一个候选项 a，RPMT 的逻辑成员位为：

$$b=\begin{cases}1,&a\in B,\\0,&a\notin B.\end{cases}$$

Alice 作为随后 OT 的发送方准备候选 \((a,\bot)\)，Bob 作为接收方按成员位选择：缺少时 b=0 得到 a，已有时 b=1 得到占位符。Alice 不知道 Bob 的选择。

在示例中，a=2 时 Bob 获得 2；a=6 时 Bob 获得占位符。合并自己的 \(\{6,8\}\) 后得到 \(\{2,6,8\}\)。按上层要求双方共同获得并集。

这里特别容易误读：**不能把教学表中的 a=2、a=6 与真实候选项的公开位置一一暴露。**如果 Bob 同时看到明文候选、它的位置和成员位，可能知道哪些自己已有元素也属于 Alice，从而泄露额外交集信息。真实 PSU 依赖整体分桶、置乱及成员测试接口的安全性，不能只把裸成员测试和 OT 两行拼起来就当完整实现。

RPMT 本身可能由 OPRF 等协议构造，但这不等于 PSU 调用了本文图 7 的那次 MROPRF。本文没有重新展开底层 PSU 的所有子协议；上层看的是它的输入、输出和泄露保证。

**本块用到：**哈希组织数据、私有成员测试、OT 和占位符。**本块没有使用：**通过多项式零点解密判断 APSI 匹配。两者虽然都处理集合，求并和求交的功能不能互换。

## 5. 第四章 IV-B 多轮 OPRF：盲化、去盲化与跨轮隐私

这一节先固定角色：Alice 是持有长期密钥 k_x 的一方，Bob 持有本轮新增输入；反方向时两人的角色交换。目标不是立刻求交，而是让 Bob 得到 Alice 密钥下的输入标签。记 \(f_k(z)=F(H(z)^k)\)。

### 5.1 随机盲化不会改变最终函数值

考虑 Bob 查询 Alice 的一个方向。Alice 持有固定 \(k_x\)，Bob 在第 \(i\) 轮**重新随机采样非零盲化指数** \(r_i\)。本文图 7 用 \(k_{y,i}\) 表示这个量；这里写成 \(r_i\)，避免与 Bob 维护自己数据库的长期密钥 \(k_y\) 混淆。

设群的素数阶为 \(q\)，则 \(r_i\in\mathbb Z_q^*\)，保证可求逆。流程是：

| 步骤 | 执行方 | 操作与通信 |
| --- | --- | --- |
| 盲化 | Bob | 计算 \(Q=H(y)^{r_i}\)，发给 Alice |
| 带密钥计算 | Alice | 计算 \(E=Q^{k_x}\)，返回 Bob |
| 去盲化 | Bob | 计算 \(E^{r_i^{-1}}=H(y)^{k_x}\)，再计算 \(F\) |

这里 \(r_i^{-1}\) 是 **模群阶 \(q\) 的乘法逆元**，不是负数 \(-r_i\)，也不是模底层整数模数求逆。因为 \(r_ir_i^{-1}\equiv1\pmod q\)，才有：

$$\bigl(H(y)^{r_i k_x}\bigr)^{r_i^{-1}}=H(y)^{k_x}.$$

长期密钥固定时，相同输入的最终标签保持不变，这是与已有数据库匹配所需要的性质。随机数在去盲化时被消去。

### 5.2 一个完整的两轮数字例子

下面只是验证代数的小例子，不具有密码学安全性。固定参数：模数 \(p=23\)，使用阶 \(q=11\) 的子群；约定示例输入 \(a\) 的群哈希为 \(H(a)=4\)。Alice 的长期密钥随机采样结果假设为 \(k_x=3\)。

两轮 Bob 的随机采样结果分别假设为 2 和 5：

| 量 | 第一次查询 a | 另一次查询 a |
| --- | --- | --- |
| 本轮随机指数 | \(r_1=2\) | \(r_2=5\) |
| 发给 Alice | \(4^2\bmod23=16\) | \(4^5\bmod23=12\) |
| Alice 返回 | \(16^3\bmod23=2\) | \(12^3\bmod23=3\) |
| 模 11 的逆元 | \(2^{-1}=6\) | \(5^{-1}=9\) |
| Bob 去盲化 | \(2^6\bmod23=18\) | \(3^9\bmod23=18\) |
| 最终标签 | \(F(18)\) | \(F(18)\) |

核对：\(4^3\bmod23=18\)。两轮消息不同，输出相同；这两件事并不矛盾。真实大群中，简单比较消息是否相等不足以建立输入关联，更强的安全性依赖群假设和完整协议证明。

### 5.3 为什么“普通 OPRF 不具备前向安全”说得太宽

你提出的反问很关键：“普通 DH-OPRF 不是每次也用新随机数盲化吗？那为什么它不行？”

**仅凭“普通 OPRF”这个名称，不能判定它跨轮不安全。**如果原协议每次确实使用新随机盲化，并有适合的多次执行安全保证，就不能因为论文另起了 MROPRF 名称而断言它必然泄露重复输入。

原论文 IV-A 针对的是直接沿用特定非对称 PSI 的生成方式来做持续更新，指出重复出现的 mask 会暴露“添加—删除—再添加”的关系；IV-B 再为自己的多轮生成过程规定功能并给出论证。阅读时必须追踪：**谁看到了哪个值，这个值在哪一轮重复，以及这种关联能否由允许公开的交集推导。**

特别区分下面三层：

| 层次 | 谁能看到 | 是否应直接随轮次改变 |
| --- | --- | --- |
| 发给密钥方的盲化消息 | 密钥方 | 新鲜随机数使消息随机化 |
| 去盲化后的函数值 | 输入方 | 固定密钥、相同输入时保持一致 |
| PSI 查询和返回消息 | 按 APSI 协议规定 | 需要该协议保护，不能直接裸发确定性标签 |

你问的“如果 Bob 把最终 \(H(y)^{k_x}\) 发给 Alice，不也能关联吗？”答案是：**如果真的这样直接发送，确实可能重新引入关联；本文后续调用的是 APSI 查询阶段，而不是裸标签交换。**不能只检查 OPRF 前半段随机化，就认为后续任意发送方法都安全。

### 5.4 谁发标签、发一批还是逐个发，由 PSI 决定

OPRF 只规定输入方如何获得函数值，不规定整个 PSI 的输出方和标签交换方向。有些简单 PSI 会由 Alice 发送数据库标签，让 Bob 本地比较；有些方案保护查询或数据库后再执行安全匹配。不能把其中一种流程当成 OPRF 的固定后半段。

“把标签放进集合一次发送”也不会自动隐藏重复。只要对方能看到稳定标签，就能比较两轮集合的交集，不需要知道标签对应的真实姓名。打乱顺序主要隐藏位置，无法隐藏相等性。

本文的前向安全讨论是**更新历史的额外关联泄露**，不要直接等同于其他语境中“长期密钥泄露后过去会话仍安全”的前向保密定义。交集本身透露的历史也无法凭随机盲化消除：如果双方每轮都得到交集，某个元素进出交集的变化本来就是允许的输出信息。

**本节用到：**群指数、模逆元、哈希、随机盲化。这里还没有靠同态加密判断成员关系，也没有运行 PSU。

### 5.5 重新走一遍追问：泄露究竟发生在哪一条消息上

设 Bob 第 1 轮加入一个始终不属于 Alice 的私有元素 a，第 2 轮删除它，第 3 轮重新加入。因为 a 始终不在交集中，Alice 从三轮交集输出中本来不能知道这段历史。

如果某种直接移植的实现让 Alice 第 1、3 轮都观察到同一稳定标记 t，她就能知道“两轮包含同一个对象”，即使仍不知道 a 的明文。这正是需要检查的额外关联。

现在分别检查三个候选位置。**位置一：Bob 发给 Alice 的盲化输入。**若使用新的随机指数，这里观察到的是不同随机化消息；不能因为原始输入相同就直接比较出相等。**位置二：Bob 去盲化后的标签。**该标签确定，但目前只由 Bob 获得；Bob 当然知道自己重复输入了什么，这不等于泄露给 Alice。**位置三：后续求交通信。**若 Bob 为了省事把最终标签裸发回 Alice，或者复用可关联的查询状态，才可能使前面的保护失效。本文实际调用的是受保护的 APSI 查询，不能假设这一步就是裸发标签。

这也解释了你说的“r 和每轮 k_y 不就是类似作用吗”：从盲化代数看，确实都是输入方的新鲜随机指数；本文的 k_{y,i} 不是替换长期标签密钥，而是被去掉的盲化指数。命名变化本身不是安全差异的证明，必须核对原协议具体复用的值及多轮安全定义。

再把角色倒过来。如果轮到 Alice 新增元素 x，由 Alice 作为输入方，Bob 持有长期密钥 k_y；此时 Alice 向 Bob 发盲化输入。这才是“Bob 会否观察到 Alice 跨轮重复新增”的对应场景。不能一边沿用 Bob 输入的流程，一边突然把 Alice 的数据库更新值说成她在 OPRF 中发出的消息。

### 5.6 标签匹配的两个方向，为什么不能凭习惯判断

在一种简单标签比较 PSI 中，Alice 可以把其数据库标签集合发给 Bob，让 Bob 在本地识别自己的匹配输入；这样主要的比较记录在 Bob 手里。另一个设计也可能把 Bob 的查询标签交给 Alice，由 Alice 比较。两者的输出与泄露方向不同。

如果收到的是一个打乱后的标签集合，接收方仍能把它与上一轮的集合求交。例如第一轮收到 \(\{t_a,t_b\}\)，第三轮收到 \(\{t_a,t_c\}\)，即便两个集合的排列不同，也能识别重复项 \(t_a\)。不知道 t_a 对应什么，并不代表不知道存在重复。

因此，回答“谁发给谁、逐个发还是批量发”时，要先指出具体 PSI 构造。本文后续处理数据库与查询标签的方式已经在 IV-A 的同态查询中交代，使用 OPRF 的函数接口并不会自动指定这些通信。

## 6. 第四章 IV-C 完整 UPSI：初始化、增删与正确性

### 6.1 H_X、H_Y 是怎样生成的

为避免把哈希、群运算和输出标签混在一起，记：

$$f_k(z)=F\bigl(H(z)^k\bigr).$$

其中 \(H\) 把元素映射到合适的群表示，指数运算发生在该群中；\(F\) 是后处理函数。实际实现需要正确的哈希到群与参数选择，不能把任意比特串直接当成群元素。

初始化时，Alice 和 Bob **分别随机采样自己的长期秘密指数** \(k_x,k_y\)，本地计算：

$$H_X=\{f_{k_x}(x):x\in X\},\qquad H_Y=\{f_{k_y}(y):y\in Y\}.$$

你曾问：“这不就是双方各用自己的密钥算的吗，怎么叫 OPRF？”这个区分是对的：

- **本地计算 PRF 表示：**Alice 已有输入和密钥，自己算 \(f_{k_x}(x)\)，没有交互。
- **执行 OPRF：**Bob 有输入 \(y\)，Alice 有密钥 \(k_x\)，通过交互让 Bob 获得 \(f_{k_x}(y)\)，双方不直接交换输入和密钥。

两者使用相同的目标函数，但获得函数值的方式不同。

由于密钥不同，\(H_X,H_Y\) 不能直接拿来比较。即使 \(x=y\)，\(f_{k_x}(x)\) 与 \(f_{k_y}(y)\) 通常也不同。Bob 查询 Alice 时，必须先得到 **Alice 的密钥**下的表示；反方向同理。

### 6.2 标签不是可解密的明文掩码

这些表示可以口语化地叫标签或掩码，但不能理解成“求交后解密，就恢复出原元素”。函数值通常没有供协议调用的逆运算。

例如 Bob 新增 \(\{2,4\}\)，获得 \(\{f_{k_x}(2),f_{k_x}(4)\}\)。Bob 自己保存“输入 2 对应第一个标签，输入 4 对应第二个标签”的本地关系。查询结果告诉他第一个匹配，他就知道交集里有 2。

**恢复元素依赖自己已有的输入与对应关系，不是反向破解标签。**论文写 \(T_i=Y_i^+\cap X_i\) 是在描述功能语义；实现内部可以处理标签、密文和匹配位置，并不意味着中途把对方集合恢复成明文。

### 6.3 先看整轮的功能目标

论文图 8 计算四个中间量：

$$T_i=Y_i^+\cap X_i,\qquad V_i=X_i^+\cap Y_i.$$

$$U_i=T_i\cup V_i,\qquad U_i'=(X_i^-\cap I_{i-1})\cup(Y_i^-\cap I_{i-1}).$$

最终更新为：

$$\boxed{I_i=(I_{i-1}\setminus U_i')\cup U_i.}$$

| 符号 | 直观理解 | 谁先知道 |
| --- | --- | --- |
| \(T_i\) | Bob 新增元素中，已经在 Alice 当前集合里的部分 | Bob，通过第一次 APSI |
| \(V_i\) | Alice 新增元素中，已经在 Bob 当前集合里的部分 | Alice，通过反方向 APSI |
| \(U_i\) | 本轮新进入交集的元素 | 双方，通过第一次 PSU |
| \(U_i'\) | 旧交集中本轮失效的元素 | 双方，通过第二次 PSU |

**这里必须使用更新后的 \(X_i,Y_i\)。**这样如果双方同一轮都新增 8，两次查询仍然能发现 8。若只查对方上一轮的集合，就可能漏掉双方同时新增的元素。

某个元素可能同时出现在 \(T_i,V_i\) 中，并集会自动去重，不会把它算两次。

现在先把这些公式理解成目标功能；双方在实际执行时不会直接交换私有更新集合来计算它们。

### 6.4 初始化与本地维护

固定示例输入：

$$X_0=\{1,2,3,4,5\},\qquad Y_0=\{3,4,5,6,7\},\qquad I_0=\{3,4,5\}.$$

这些集合是人为设定的教学数据，不是协议随机数。双方通过一次基础 PSI 得到 \(I_0\)，另各自随机生成长期密钥、建立可复用的 APSI 数据库状态。论文实现使用 RR22 作基础 PSI；理论框架可使用符合要求的其他 PSI。

本轮 Alice 删除 \(\{3\}\)、新增 \(\{6,8\}\)；Bob 删除 \(\{4\}\)、新增 \(\{2,9\}\)。因此：

$$X_1=\{1,2,4,5,6,8\},\qquad Y_1=\{2,3,5,6,7,9\}.$$

双方先在本地删除相应标签、加入新标签，并维护数据库。**本地维护不等于把增删标签发给对方，也还没有完成新交集计算。**

### 6.5 两个方向，各一次 MROPRF 和 APSI 查询

| 方向 | OPRF 输入方 | 使用的长期密钥 | APSI 查询目标 | 得到的结果 |
| --- | --- | --- | --- | --- |
| Bob 查询 Alice | Bob，输入 \(Y_1^+\) | Alice 的 \(k_x\) | \(Y_1^+\cap X_1\) | Bob 得到 \(T_1=\{2\}\) |
| Alice 查询 Bob | Alice，输入 \(X_1^+\) | Bob 的 \(k_y\) | \(X_1^+\cap Y_1\) | Alice 得到 \(V_1=\{6\}\) |

查询前双方已经分别更新本地集合。Bob 使用新鲜盲化获得 2、9 在 \(k_x\) 下的标签；Alice 使用反方向的新鲜盲化获得 6、8 在 \(k_y\) 下的标签。随后调用相应 APSI 查询。

只算一个方向会漏项：只查 Bob 的新增会漏掉 6，只查 Alice 的新增会漏掉 2。

### 6.6 第一次 PSU：合并新进入交集的元素

Bob 私有输入 \(T_1=\{2\}\)，Alice 私有输入 \(V_1=\{6\}\)，双方通过规定的 PSU 接口共同得到：

$$U_1=T_1\cup V_1=\{2,6\}.$$

为何不直接互发 \(T_1,V_1\)？直接发送会暴露中间集合的来源和结构；PSU 的目标是只按其功能公开并集。并集当然也会揭示一些输入事实，例如 Alice 知道自己的输入，就知道并集中不属于自己输入的项来自对方；安全性从来不是“从结果中推不出任何信息”。

**本文上层需要双方都获得并集。**底层实现还须匹配输出方、输入规模泄露等要求，不能把任意同名 PSU 库直接替换。作者仓库当前说明也强调了双输出和隐藏精确输入规模的接口要求；这是使用版本时要核对的细节。[作者实现说明](https://github.com/ShallMate/upsi)

### 6.7 删除阶段的交集在本地算，第二次 PSU 才需要交互

旧交集 \(I_0\) 已经由双方知道。Alice 自己知道删除集合，于是本地算：

$$D_X=X_1^-\cap I_0=\{3\}.$$

Bob 本地算：

$$D_Y=Y_1^-\cap I_0=\{4\}.$$

这两次普通求交**不需要 APSI**。例如 Alice 已有自己的删除哈希表和旧交集，扫描少量删除元素并查询即可。即使“一个集合大、一个集合小”，也没有必要为了规模不对称而加一层密码协议。

APSI 适用于双方分别持有需要保护的输入。这里同一方已经拥有完成本地计算所需的两个输入，直接算通常更简单。

然后双方调用第二次 PSU，得到：

$$U_1'=D_X\cup D_Y=\{3,4\}.$$

私有的完整删除集合没有因此直接公开；原本不在旧交集中的删除元素，也无需进入这一 PSU 的输入。

### 6.8 本地组合出新交集

$$I_1=(\{3,4,5\}\setminus\{3,4\})\cup\{2,6\}=\{2,5,6\}.$$

直接检查 \(X_1\cap Y_1\)，同样是 \(\{2,5,6\}\)。最终组合不需要额外交互。

因此，**图 8 一轮非空更新的结构是两次 MROPRF、两次 APSI 查询、两次 PSU**。初始化的基础 PSI 不算每轮重复调用；删除时两次本地普通交集也不计作 APSI。空更新可以按实现跳过无用步骤，不能据此混淆协议的两方向结构。

### 6.9 为什么还需要正确性证明

你曾问：“公式按步骤执行本来就对，为什么还要证明？”关键区别在于：算对一个例子，不代表任意合法更新都正确。

正确性需要同时排除两类错误：该留下的元素没留下，或者不该在交集里的元素被加进来。

### 6.10 新交集不会漏掉任何元素

任取 \(z\in X_i\cap Y_i\)：

- 若 \(z\) 原本就在旧交集中，且本轮后仍在两边，那么按更新规则它未被任意一方删除，故留在 \(I_{i-1}\setminus U_i'\)。
- 若 \(z\) 原本不在旧交集中，现在两边都有，至少有一方本轮新增了它。Bob 新增则属于 \(T_i\)，Alice 新增则属于 \(V_i\)，所以属于 \(U_i\)。

双方同时新增也包括在第二种情况里，并集去重即可。

### 6.11 组合结果不会多出错误元素

- \(I_{i-1}\setminus U_i'\) 里的元素原来两边都有，且未被任何一方删除，所以现在仍两边都有。
- \(T_i\) 的元素来自 Bob 的新增，又属于 Alice 当前集合，所以两边都有。\(V_i\) 同理。

两边包含关系都成立，才得到任意合法输入下的等式。这是**集合层面的正确性**；同态运算和底层协议自身的正确性还依赖相应参数和失败概率分析。

### 6.12 先明确目标：协议算出的集合，不能预先叫作真实交集

后续推导固定记：

$$I_i=X_i\cap Y_i\quad\text{（真实新交集）},\qquad \widehat I_i=(I_{i-1}\setminus U_i')\cup U_i\quad\text{（执行 UPSI 得到的集合）}.$$

要证明的是 \(\widehat I_i=I_i\)，而不是把等号先当定义写上后，再声称证明完成。所有 \(U_i,U_i'\) 均从协议的两个局部交集和删除部分定义出发。

论文 IV-C 用双向包含法；下面先把会话中后续追问的集合等式证明写完整，再将它们代入，给出另一条便于讲解的正确性推导。**这条展开路线不是声称原文 IV-C 原样如此写。**

### 6.13 准备四条规则：每次变形要知道用了哪条

| 规则 | 公式 | 为什么成立 |
| --- | --- | --- |
| 规则 1：差集对交集的德摩根律 | \(A\setminus(B\cap C)=(A\setminus B)\cup(A\setminus C)\) | 不同时属于 B、C，就是至少不属于其中一个 |
| 规则 2：交集内移差集 | \((A\cap B)\setminus C=(A\setminus C)\cap B=A\cap(B\setminus C)\) | 保留属于 A、属于 B、又不属于 C 的元素 |
| 规则 3：从 A 中去掉 A 外于 B 的部分 | \(A\setminus(A\setminus B)=A\cap B\) | A 中剩下的恰好是也属于 B 的元素 |
| 规则 4：按是否属于 A 划分 B | \((A\cap B)\cup(B\setminus A)=B\) | B 的元素或者在 A 中，或者不在 A 中，两部分覆盖全部 B |

这些是集合恒等式，不是密码学假设。可以把差集读为“属于左边且不属于右边”，把并集读为“或者”，把交集读为“并且”，就能逐元素检查它们。

### 6.14 为什么新增集合等于“本轮集合减上一轮集合”

合法更新下有：

$$X_i^+=X_i\setminus X_{i-1},\qquad Y_i^+=Y_i\setminus Y_{i-1}.$$

先证 Alice 一侧。若元素在 \(X_i^+\)，新增不在旧集合的规则保证它不在 \(X_{i-1}\)，同时添加后它在 \(X_i\)，故属于右边。反过来，若元素本轮在 \(X_i\) 而上一轮不在，它不可能来自保留的旧元素 \(X_{i-1}\setminus X_i^-\)，只能来自新增集合。因此两边互相包含。

例如旧集合 \(\{1,2,3\}\)，删除 1、新增 4，当前是 \(\{2,3,4\}\)，当前减旧集合就是 \(\{4\}\)。这里不是“把变量名称换一下”，而是先证明新增集合与这个差集是同一个集合。

### 6.15 证明 U_i：从真实新旧交集展开到协议定义

协议定义为：

$$U_i=(Y_i^+\cap X_i)\cup(X_i^+\cap Y_i).$$

从另一侧展开会更清晰。第一步代入真实新、旧交集的定义：

$$I_i\setminus I_{i-1}=(X_i\cap Y_i)\setminus(X_{i-1}\cap Y_{i-1}).$$

第二步使用**规则 1**，将“去掉一个交集”拆成两个差集的并集：

$$=[(X_i\cap Y_i)\setminus X_{i-1}]\cup[(X_i\cap Y_i)\setminus Y_{i-1}].$$

第三步使用**规则 2**，把差集移到对应一侧：

$$=[(X_i\setminus X_{i-1})\cap Y_i]\cup[X_i\cap(Y_i\setminus Y_{i-1})].$$

第四步才是代入已证明的新增集合表达式，并用交集、并集交换律：

$$=(X_i^+\cap Y_i)\cup(X_i\cap Y_i^+)=V_i\cup T_i=U_i.$$

因此 \(U_i=I_i\setminus I_{i-1}\)。这段同时用了“新增集合的等价表达”“集合恒等式”“最后按 T、V 的定义识别”，不只是变量代换。

直观上：现在属于两边、以前没有同时属于两边的元素，至少有一方是在本轮新增了它。因此两次 APSI 不会漏掉任何新进入交集的元素。

### 6.16 证明 U_i′：先解释删除集合为什么能变成差集

协议定义：

$$U_i'=(X_i^-\cap I_{i-1})\cup(Y_i^-\cap I_{i-1}).$$

由于 \(I_{i-1}\subseteq X_{i-1}\)，旧交集元素原本都在 Alice 集合里。对其中任意 z：如果它本轮被 Alice 删除，又不能同轮重加，那么现在不属于 \(X_i\)；如果它现在不属于 \(X_i\)，作为原本就在 Alice 集合的元素，必然被本轮删除。因此：

$$X_i^-\cap I_{i-1}=I_{i-1}\setminus X_i,\qquad Y_i^-\cap I_{i-1}=I_{i-1}\setminus Y_i.$$

先依据更新语义建立这两个等式，再代入 U′，最后反向使用**规则 1**：

$$\begin{aligned}U_i'&=(I_{i-1}\setminus X_i)\cup(I_{i-1}\setminus Y_i)\\&=I_{i-1}\setminus(X_i\cap Y_i)\\&=I_{i-1}\setminus I_i.\end{aligned}$$

直观上：一个旧交集元素现在不是共同元素了，至少有一方删除了它。两方各自删除的旧交集部分取并，恰好得到失效项。

### 6.17 最后代回协议公式：补全容易跳过的一步

现在两个中间量的等式都已证明，因此：

$$\begin{aligned}\widehat I_i&=(I_{i-1}\setminus U_i')\cup U_i\\&=[I_{i-1}\setminus(I_{i-1}\setminus I_i)]\cup(I_i\setminus I_{i-1})\\&=(I_{i-1}\cap I_i)\cup(I_i\setminus I_{i-1})\quad\text{（规则 3）}\\&=(I_i\cap I_{i-1})\cup(I_i\setminus I_{i-1})\quad\text{（交集交换律）}\\&=I_i\quad\text{（规则 4）}.\end{aligned}$$

你追问的“交集并上差集，为什么等于 I_i”就在最后两行：把 \(I_i\) 中的元素按“是否也属于旧交集”分成两类。前一部分是保留项，后一部分是新进入项，两部分合起来就是全部真实新交集，没有其他元素。这里不能只写“显然等于”就跳过去。

例如 \(I_0=\{3,4,5\}\)、\(I_1=\{2,5,6\}\)：保留项 \(I_0\cap I_1=\{5\}\)，新进入项 \(I_1\setminus I_0=\{2,6\}\)，并起来得到 \(\{2,5,6\}\)。例子帮助看懂规则 4，前面的恒等式则证明任意合法输入都成立。

这一结论说明执行 UPSI 得到的集合等于重新对当前完整集合求交的结果。证明中用到的是更新假设和集合规则，没有再调用一次密码学 PSI 来“验证”结果。

## 7. 第四章 IV-D 隐私分析：中间结果是否超出允许输出

### 7.1 Alice 不知道 Bob 的 T_i，仍然可以得到 U_i

Alice 并没有在本地拿到 Bob 的全部新增、删除集合。各自私有输入通过 PSU 使用，Alice 得到的是接口允许输出的并集。

但“协议如何算出”与“最终能否从允许信息重建”是两个问题。论文 IV-D 的隐私分析证明，在前述更新规则下：

$$V_i=X_i^+\cap I_i,\qquad U_i=I_i\setminus I_{i-1},\qquad U_i'=I_{i-1}\setminus I_i.$$

因此 Alice 一旦知道自己的输入以及允许公开的新旧交集，就能重建她获得的这些中间输出，而不需要知道 Bob 的完整 \(Y_i^+,Y_i^-\) 或 \(T_i\)。

在完整例子中，已知 \(I_0=\{3,4,5\}\)、\(I_1=\{2,5,6\}\)，直接做差便能得到新增交集 \(\{2,6\}\) 与失效交集 \(\{3,4\}\)。这部分信息原本就在输出历史中。

### 7.2 “可由输出推出”不等于“过程随便公开也没事”

Alice 可以从结果知道 4 不再属于交集，但这不意味着应该把 Bob 的全部删除集合交给她。特别是双方都可能删除同一个旧交集元素时，公开每方的具体贡献可能透露比并集更多的信息。

同样，两个中间集合的精确大小也未必能从并集大小确定。**不仅集合内容，子协议的输入规模、消息长度和跨轮关联都要符合允许泄露。**这正是使用真实组件时必须核对接口的原因。

本节证明的是中间**输出内容**可推导，不是在宣称任意实现、任意报文都安全。

### 7.3 把“协议执行”与“隐私论证时的重建”分成两条线

以 Alice 为例：实际执行时她先通过反方向 APSI 得到 V，通过 PSU 得到 U、U′，最后更新出新交集。她没有先得到 Bob 的 T 或完整删除集合。

证明时顺序相反：假设已经把理想功能允许的自身输入、新旧交集交给一个模拟者，问它能否重建 Alice 在真实执行中看到的中间输出。前面证明的差集等式就是为这条线服务的。它不是说实际协议必须预先知道新交集才能执行，否则确实会形成循环。

例如 Alice 知道新增 \(X_1^+=\{6,8\}\)，允许的新交集是 \(\{2,5,6\}\)，于是模拟者可算出 V=\(\{6\}\)；从旧、新交集又可推出 U=\(\{2,6\}\)、U′=\(\{3,4\}\)。重建这些输出并不需要 Bob 的完整新增 \(\{2,9\}\) 或删除集合。

这回答了“U 的定义里明明有 T，Alice 不知道 T 怎么说不泄露”：**能通过安全计算得到函数结果，不要求先知道对方输入；而证明输出不额外泄露，靠的是存在另一种只使用允许信息的等价表达。**

## 8. 第四章 IV-E 复杂度分析：每一阶段的成本来自哪里

### 8.1 初始化和每轮更新要分开

初次运行包含建库与基础 PSI，后续轮次复用这些状态。论文更新复杂度分析不包含一次性初始化；实际应用若只运行一两轮，初始化成本仍然不能忽略。

在等规模假设、论文采用的组件和复杂度口径下，IV-E 总结更新计算复杂度为：

$$O\bigl(N^u\log N+\sqrt N\bigr),$$

通信复杂度为：

$$O\bigl(N^u+\log^2N\bigr).$$

\(\sqrt N\) 等项提醒我们：更新并非完全摆脱大集合影响。换 PSU 实现时也要检查它的计算复杂度，不能把理论推荐组件与实际工程组件的界完全混为一谈。

论文实验使用 YACL、APSI、RR22 和 KRTW PSU；理论部分推荐更优渐近复杂度的 PSU，但实现整合便利性也是选择因素。替换一个模块能改进多少，要看该模块占总时间的比例。



### 8.2 按图 8 拆开计算，理解这些项从哪里来

删除和添加在本地维护编码数据库。论文在相应数据结构假设下，将每阶段维护记为 O(Nᵘ log N)，不产生双方通信。两次 MROPRF 各处理少量新增项，数量级随 Nᵘ 增长；两次 APSI 查询的大集合访问仍带来依赖 N 的成本，论文合并后保留了平方根项。

两次 PSU 的输入是局部新增交集，以及删除对旧交集的影响，均受本轮更新规模约束，使用线性组件时为 O(Nᵘ) 量级。最后的集合更新同样围绕受影响元素进行。常数 2 在大 O 记号里会被省略，但真实运行时间不能忽略两次调用。

这里应区分抽象集合操作与实际表示：若程序每轮扫描完整旧交集，或重建全部数据库，真实开销就不能只套少量更新的渐近界。理论算法、库接口和工程实现需要逐一对照。

## 9. 第四章 IV-F 安全证明：理想功能与真实协议的关系

### 9.1 理想组件是证明用的接口，不是现实中的可信服务器

可以把理想 PSI 想成一台可信计算机器：双方提交私有集合，它只给规定的结果方交集和允许泄露的信息。理想 PSU 只给规定的并集；理想 MROPRF 只向输入方给规定函数值。

现实协议使用密码学消息实现这些功能。证明时先把部分组件当作理想黑盒，就能暂时不展开每个 OT、密文和哈希操作，集中检查上层组合。这叫在相应的混合模型中分析。

所以，作者并不是“提了一嘴理想组件却没有用到”。图 8 明确调用基础 PSI、两方向 MROPRF、APSI 查询和 PSU；实际程序再用具体算法实现它们。

### 9.2 模拟证明真正要说明什么

半诚实参与方遵守计算步骤，但可以保存全部记录，分析输入、随机数、收到的消息和所有轮次的状态。目标是证明：这些记录没有带来理想功能以外的有效信息。

模拟器的思路是：**仅给它该参与方自己的输入、允许的输出与泄露，它仍能生成与真实视图不可区分的记录。**如果做得到，观察者就没有通过真实执行获得额外信息的可靠方法。

例如模拟 Alice 的中间输出时，可从 \(X_i^+,I_{i-1},I_i\) 算出上一节的 \(V_i,U_i,U_i'\)，再借助子协议各自的模拟保证处理通信。这里是在解释证明框架，不是替原文补出一份完整模拟器。

### 9.3 底层安全与上层无额外泄露必须接起来

完整论证至少包含三层：

1. **组件安全：**实际 PSI、PSU、MROPRF 和 APSI 查询要满足对应功能、模型和泄露接口。
2. **组合安全：**检查中间输出、状态与跨轮联合视图，不能只单独看每条消息。
3. **替换条件：**使用适用的组合结论，把理想组件替换成真实协议，保持所需安全保证。

同态加密只承担其中一部分工作：Alice 处理 Bob 的查询密文时，不应看到查询明文。Bob 解密到的响应是否泄露额外代数信息、数据规模是否暴露、跨轮是否可关联，并不能靠“用了加密”这四个字自动解决。

论文 IV-B 给出 MROPRF 的定理和基于 DDH 的论证；DDH 粗略地说是难以区分 \((g,g^a,g^b,g^{ab})\) 与末项独立随机的群元组。IV-F 的整体 UPSI 证明则非常简短，依赖理想组件和同态加密查询。IV-D 原文也明确说明，其推导不是正式的模拟式安全证明。

**汇报时可以这样说：**论文在半诚实模型下采用模块化安全论证。中间输出能由自身输入与允许的新旧交集重建；具体通信安全依赖底层组件和适用的组合条件。原文整体证明较简略，不能把它解释成“任意几个安全库拼接后就一定安全”，也不能直接推广到恶意参与方或长期密钥泄露场景。

### 9.4 把模块化论证拆成一次真实执行、一次理想执行

真实世界中，Alice 收到多轮盲化消息、查询密文、PSU 消息，持有自己的随机数和全部本地状态。理想世界中，可信功能只给她规定的交集、规模和其他允许输出。模拟器要用后者造出前者的视图，让有效观察者分不出真假。

第一步，暂时把基础 PSI 和 PSU 等当作理想接口。上层仍会看到这些接口返回的集合，因此必须证明 V、U、U′ 没有超出允许输出。这由隐私分析中的等式解释。

第二步，底层真实协议替换理想接口时，还要保证接收方是谁、输入和输出是否为共享、长度泄露、调用顺序、状态是否复用等都满足证明条件。组件名字相同但接口不同，就不一定可以替换。

第三步，对不完全抽象掉的 APSI 查询、跨轮 MROPRF 等，需要其本身的安全保证。比如仅知道 Alice 收到的是密文，不足以判断 Bob 解密响应时会学到什么，也不能说明多个轮次的联合记录无关联。

所以“存在理想 PSI、PSU、MROPRF 时安全”是在说**一个混合模型中的分析起点与组合思路**，不是说现实世界凭空出现了几个可信服务，也不是一句话就完成所有真实协议的证明。论文 IV-F 确实写得很短；学习时应理解依赖关系，不替它声称已经展开了原文没有给出的所有模拟细节。

如果组会被问“你到底证明什么”，可以先回答：真实参与方的完整视图没有超出自身输入和理想功能允许输出的信息；再说明中间输出可重建、子协议安全及替换条件这三层，而不要只回答“同态加密，所以安全”。

## 10. 第四章 IV-G 单向 UPSI：为什么要共享中间结果

### 10.1 不发送最终结果，无法撤回之前已经知道的内容

原构造让双方都得到交集。在半诚实语境中，论文把它称为 fair UPSI；不要由此推断它提供了恶意中止下的一般公平性保证。

若要改成“只有 Bob 知道交集”，仅在最后不把 \(I_i\) 给 Alice 不够。反方向 APSI 已让 Alice 知道 \(V_i\)，删除步骤又默认她知道 \(I_{i-1}\)。这些信息早已违背单向目标。

### 10.2 不是 Alice 先得到 V_i，再把它拆成份额

若 Alice 已看到真实 \(V_i\)，事后秘密共享无法让她忘记。正确目标是：**APSI 从一开始只输出份额，Alice 从未恢复中间交集。**

用成员向量解释份额。假设某个概念性候选域上的真实成员位为 \(v=(0,1,1)\)，协议内部**均匀随机采样** Alice 的份额 \(s_A\)，假设本次采样结果为 \((1,0,1)\)，并生成：

$$s_B=v\oplus s_A=(1,1,0),\qquad s_A\oplus s_B=v.$$

单独一份不能确定 \(v\)。此例仅解释异或共享，候选域如何隐藏、集合如何表示及长度如何处理，都属于实际协议设计，不能把私有候选列表直接公开给对方。

### 10.3 支持共享输入的 PSU 是什么意思

普通 PSU 接受双方分别知道的明文集合。共享输入版本需要直接使用双方持有的份额参与安全运算，不先公开恢复共享集合。

从成员位看，并集是 OR。对秘密位 \(a,b\)，在 \(\mathbb F_2\) 中有：

$$a\lor b=a\oplus b\oplus ab.$$

异或部分可线性处理，乘积一般还需安全乘法、OT 或其他 MPC 机制。不能把两份任意异或后就声称实现了私有集合并集。

单向 UPSI 希望安全组合 \(T_i\) 与共享的 \(V_i\)，只向 Bob 输出所需结果；删除部分也要解决 Alice 不知道旧交集时如何计算的问题。论文 IV-G 提出共享输出 APSI、共享输入 PSU 这两个方向，**把高效具体实例化留作后续问题**，并未给出已经完成的完整单向实现。

### 10.4 一个共享输入求并的概念性例子

设 Bob 的某些候选成员位是 \(t=(1,0,0)\)，另一中间结果 v 不公开，只由双方持有异或份额 \(s_A=(1,0,1)\)、\(s_B=(1,1,0)\)。安全计算内部相当于 v=\(s_A\oplus s_B=(0,1,1)\)，并集成员位应为 \(t\lor v=(1,1,1)\)。

这句话是在说明目标函数，**不是让双方真的先交换份额公开 v**。输入共享的 PSU/MPC 要在不暴露 v 的情况下得到相应输出，再只交给许可结果方。两份秘密输入继续被使用，和把它恢复成明文后普通求并，是两种不同接口。

若 Alice 先获得 v 再采样份额，她早已知道匹配情况，不满足这里的单向要求。共享输出 APSI 要直接在执行末尾生成份额；协议开始到结束都不能让她提前见到真实 v。

## 11. 第五章 实验评估：初始化、对比结果与更新阈值

### 11.1 第五章先看实验设置与基线，再看提升倍数

论文使用工作站上的两个 Docker 容器模拟双方，CPU 为 Intel Xeon Gold 6230R，内存 128 GB，系统 CentOS；计算安全参数 128 位，测试元素为 128 位。LAN 与 WAN 的带宽和 RTT 一起变化，因此比较 LAN 与 WAN 时不能把全部时差都归因于带宽。

初始化表记录基础 PSI 与可复用状态的准备；更新表记录已有状态后的一轮更新；对比表把 RR22、其他 UPSI 与本文放在相应配置下比较；阈值图表再改变更新规模，寻找重跑完整 PSI 更划算的位置。这四类实验回答不同问题。

初次建库不会免费消失。若初始化耗时较多、以后会更新很多轮，可以摊销；若只进行一次更新，把初始化全部排除后宣传“总流程更快”就不合理。本地复现也应写明计时边界。

相对于另一篇论文的结果，还要核对其实现是否可用、是否直接采用原作者报告的时间、支持功能是否相同。本文对某个无公开实现的比较对象使用其报告数据，因此不能把所有比较都当成同一机器重跑得出。



### 11.2 带宽低，为什么相对优势反而更大

用一个便于理解的近似模型：

$$T\approx T_{\mathrm{compute}}+\frac{S}{B}+R\cdot\mathrm{RTT}.$$

这里 \(S\) 是传输量、\(B\) 是有效传输速率、\(R\) 是受延迟影响的交互轮数。计算与通信可能重叠，实际时延不能仅按此式精确相加；字节与比特也必须统一。

重新完整 PSI 通常传输更多数据；少量更新的 UPSI 通信较少，但仍需 OPRF、同态查询和 PSU 运算。提高带宽会减轻前者的通信负担，却不会直接消除后者的密码计算成本。

所以，低带宽下 UPSI 可能有更大**相对优势**，不表示低带宽让 UPSI 自己跑得更快。

### 11.3 按表 III 原值读一组数据

以下是期刊版表 III 中 \(N=2^{22},N^u=2^{10}\) 的数据，单位为秒；LAN 为 1 Gbps、RTT 0.2 ms，WAN 三档 RTT 为 80 ms：

| 环境 | RR22 重新完整求交 | 本文 UPSI 更新 | 如何理解 |
| --- | ---: | ---: | --- |
| LAN | 8.17 | 9.14 | RR22 略快 |
| 200 Mbps | 18.87 | 9.81 | UPSI 约快 1.92 倍 |
| 50 Mbps | 49.77 | 10.60 | UPSI 约快 4.70 倍 |
| 5 Mbps | 420.57 | 20.09 | UPSI 约快 20.93 倍 |

这组通信量分别为 RR22 的 206.65 MB 与 UPSI 的 5.27 MB，约相差 39.2 倍。通信比不等于运行时间比，因为两者的计算工作不同。

**阅读纠错：**会话中曾把这一行 RR22 的 50 Mbps 时间写成 19.77 秒，原表是 **49.77 秒**。另外，论文正文讨论同一 \(N,N^u\) 的 5 Mbps 情形时出现 17.29 秒，但表 III 中 \(N^u=2^{10}\) 对应 **20.09 秒**；17.29 秒列在 \(N^u=2^8\) 行。本文按原表对应行记录，保留原文不一致的事实，不猜测作者原因。

### 11.4 表 IV 的横线，不等于“永远是 PSI 更快”

表 IV 给出作者报告的有效更新阈值；超过一定更新量，重新运行完整 PSI 可能更合算。

| 带宽 | \(N=2^{18}\) | \(N=2^{20}\) | \(N=2^{22}\) |
| --- | --- | --- | --- |
| 200 Mbps | — | — | \(2^{11}\) |
| 50 Mbps | \(2^7\) | \(2^{11}\) | \(2^{12}\) |
| 5 Mbps | \(2^{11}\) | \(2^{13}\) | \(2^{15}\) |

表注的意思是：横线对应的测试参数下，重新执行基线 PSI 更占优。**这是实验总结，不是对所有硬件、实现、输入分布和任意更新量的数学证明。**

而且原表之间存在需要保留的疑点：表 IV 对 \(N=2^{20}\)、200 Mbps 标横线，但表 III 在 \(N^u=2^8\) 时报告 RR22 为 4.30 秒、UPSI 为 3.74 秒，后者反而略快。原文没有充分解释这个差异，因此不宜把横线强解读为“任何更新量下 UPSI 都慢”。

阈值应理解为测量出来的选择依据。部署时需要在自己的机器、参数和网络上重测，特别留意双方更新量是否符合论文的等规模口径。

### 11.5 不同论文之间的优势不能混成一个倍数

表 III 同时比较普通 PSI、只增不删 UPSI、支持增删 UPSI，以及考虑前向隐私的方案。功能范围与测量来源不同，不能把“相对某个昂贵的增删协议提升几个数量级”写成“比所有 PSI 都快几个数量级”。

可用于复习的结论是：**大集合、相对小更新、昂贵通信通常更有利于本文方案；高速网络或较大更新量下，重新运行高效完整 PSI 可能更好。**

### 11.6 第 V-F 节：换更快 PSU 是否能让整体同样快

论文还比较了采用的 PSU 与另一更快 PSU，并估算替换收益。一轮调用两次 PSU，若一次从 a 秒下降到 b 秒，其他环节不变，理论上总时间减少约 \(2(a-b)\) 秒，而不是把整体时间直接按 a/b 倍缩小。

这是因为 APSI 查询、MROPRF 和维护成本仍然存在。它也提示复现时先按阶段计时：瓶颈若主要在同态查询，单独加速 PSU 的收益有限。这是组件性能和端到端性能的区别，不是说 PSU 优化没有价值。

## 12. 第六章 应用：动态数据对齐与研究边界

论文讨论纵向联邦学习的数据对齐、医疗数据共享、社交网络分析。三者的共同点是：匹配对象不断变化，希望维护共同记录，减少重复全量求交。

不过 PSI 只负责匹配阶段。它不会自动保护后续训练、病历查询或社交关系分析产生的所有信息；允许输出的交集历史本身也需要应用方评估。

结合前面的疑问，可以把后续研究问题分成四类：

| 方向 | 具体问题 | 需要继续学什么 |
| --- | --- | --- |
| 单向输出 | 不让非结果方提前得知中间交集和旧交集 | 秘密共享、共享输出 PSI、共享输入 PSU、MPC |
| 跨轮安全 | 状态、消息和规模是否暴露允许输出之外的关联 | 模拟式证明、多轮联合视图、泄露定义 |
| 实际性能 | 何时更新、何时重跑全量；更换组件有多大收益 | 分阶段计时、网络测量、初始化摊销、阈值复现 |
| 更强攻击模型 | 参与方偏离协议、输入不合法或主动构造消息怎么办 | 恶意安全、输入一致性、可验证计算机制 |

这些是进一步研究的切入点，不是声称论文已经解决。初学时先能解释图 8 各输入输出及其隐私边界，再深入具体实现会更有方向。

## 13. 第七章 总结：按整轮流程复习

| 容易混淆的问题 | 记住这一点 |
| --- | --- |
| 本地算 H_X 算不算 OPRF | 本地知道密钥与输入，不需要 OPRF 交互 |
| 两边各算自己的标签能直接比吗 | 密钥不同；查询方要先拿到对方密钥下的标签 |
| 随机盲化为何输出仍相同 | 随机指数在去盲化时被消去 |
| 普通 OPRF 一定跨轮不安全吗 | 不能一概而论，要看随机化、安全模型和后续消息 |
| 发一整个标签集合就隐藏重复了吗 | 稳定标签仍可被跨轮比较，打乱也不消除相等性 |
| 本文谁加密查询 | 小集合查询方；大集合方同态求值，查询方解密 |
| 求交后要把标签解密回原元素吗 | 用本地输入与标签、位置的对应关系识别结果 |
| 每轮 APSI 几次 | 两方向各一次查询，处理双方新增 |
| 删除时也有两次 APSI 吗 | 没有；各方本地求交，再调用第二次 PSU |
| Alice 不知道 Bob 的更新如何得到并集 | 安全子协议利用双方输入，输出规定结果 |
| 中间输出为何不额外泄露 | 能从自身输入及允许的新旧交集重建，仍要检查通信与规模 |
| 组件安全能直接推出整体安全吗 | 还需要接口匹配、联合泄露分析与适用的组合条件 |
| 秘密共享能让已经知道的结果忘掉吗 | 不能；协议须一开始就只输出份额 |
| N、Nᵘ 必须双方相等吗 | 等规模是论文分析设定，不是集合更新公式的限制 |
| 低带宽让 UPSI 更快吗 | 自身通常更慢，但相对完整 PSI 的优势可能变大 |
| 表 IV 横线表示永远更慢吗 | 只是测试设置下的概括，还需注意与表 III 的差异 |

把整篇文章压缩成一条主线：**先用基础 PSI 建立旧交集和本地状态，再用多轮 OPRF 对齐标签、两方向 APSI 找新增匹配、两次 PSU 合并增删影响，最后本地更新交集；安全性检查整轮联合泄露，性能则比较计算、通信与初始化摊销。**
